# S6-Runbook — der echte Modellturn, startbereit

> **Status:** plan — Anleitung für den echten Modellturn, Schritt für Schritt, ohne Schlüsselwert. **Stand:** 2026-10-17
> **Einstieg:** `docs/INDEX.md` · **Zahlen:** `docs/ZAHLEN.md` · Messvorlage: [`docs/probes/store-cost.json`](probes/store-cost.json) §4

Der Turn ist der letzte offene Beleg von S6
([`S6-MODELLTURN-AUDIT-CI-2026-10-17.md`](S6-MODELLTURN-AUDIT-CI-2026-10-17.md)):
Boot, echtes Urteil, Widerruf, Host-Ende, Neustart mit Protokoll — wie in
PLAN.md §9.1 geführt und als Wiederholung des am 2026-10-11 gemessenen Weges
(Probe #4 dort: `agnes-3.0-flash` war der Stand damals). Dieser Turn fährt
dasselbe Protokoll gegen die Route, die **im** Profil-Dump steht — am
2026-10-17 gemessen `agnes/agnes-2.5-flash` (B0-4 in
[`BATCH0-SCOPE-2026-10-17.md`](audit/BATCH0-SCOPE-2026-10-17.md)). Die Route ist
ein live-Feld: die UI schreibt sie über den `config-editor` in die Profil-Ebene,
also gilt für jeden Lauf der Dump **dieses** Laufs, nicht dieser Satz.
Die PLAN-Zeile für 3.9 nennt `agnes/agnes-3.0-flash` — genau diese Diskrepanz
benennt der Turn im Protokoll ausdrücklich; die wirksame Route entscheidet,
nicht PLAN-Text.

## 1. Schlüssel bevor irgendetwas läuft

- Der Schlüssel liegt in `.env` **im Repo-Root** (gitignored, Modus 600); `dsh`
  lädt die Datei beim Start selbst, das geseedete Home verlinkt dieselbe
  Datei. Die Repo-Regel gilt ungeändert: `chmod 600 .env`, nie committen, nie
  ausgeben, nie in Antworten kopieren.
- Jede Prüfung in [`scripts/s6-turn.mjs`](../scripts/s6-turn.mjs) liest nur den
  **Namen** der Schlüsselzeile und den Dateimodus — der Wert verlässt die
  Maschine nicht, wird nie gedruckt, nie geloggt; das Runner-Skript enthält
  keinen Codepfad, der ihn ausgäbe.
- **Welcher Name**, entscheidet die Route aus dem Dump: der Preflight liest
  `agent-default-model` und den `apiKeyEnv` seines Providers
  (`chosenRoute` in [`scripts/lib/model-route.mjs`](../scripts/lib/model-route.mjs)).
  Ein fester `AGNES_API_KEY` neben einer wählbaren Route nannte bis
  2026-10-20 den falschen Schlüssel (Route `prompter` liest
  `PROMPTER_API_KEY`) — der Name steht deshalb nicht mehr im Skript.
- `npm run s6:check` meldet Schlüsselanwesenheit, Modus, Route (die aus dem
  Dump) und den Ort des gepinnten `dsh` — Exit 0 nur, wenn Node ≥ 22, echtes
  Repo-`dsh`, Modus 600 und der Profil-Dump lesbar sind; fehlt der Name, den
  die Route liest, ist der Turn **blockiert** und der Runner sagt es mit
  Exit 1, statt Halbstart zu riskieren.

## 2. Ablauf

| # | Befehl | Erwartung |
|---|---|---|
| 1 | `npm run s6:check` | Exit 0, `route: <provider>/<model>` aus dem Dump und `key: <apiKeyEnv dieser Route> bereit über .env` |
| 2 | `npm run s6:boot` | Zeile `s6-turn: Host läuft (PID …, Port 3099 …)`; Protokoll in `logs/s6/boot-*.log`, PID-JSON daneben |
| 3 | UI-Turn | Schritte 3a–3c unten |
| 4 | `npm run s6:stop` | SIGTERM an die gelogte PID, PID-JSON gelöscht |
| 5 | `npm run s6:boot` | frischer Prozess (der Neustart-Schritt), derselbe Stand aus der Index-Ablage |
| 6 | Protokoll | Abnahme-Notiz mit Exitcodes je Schritt, Rohwerte ohne Fremdprotokoll |

**Schritt 3 — der Turn über die echte UI**, mit der Testfrage des Probe #4
(kein Repo-Inhalt, eine Neutralitätsfrage):

1. Browser auf `http://localhost:3099`; eine neue Sitzung öffnen.
2. Testfrage stellen: `Antworte genau mit dem Wort bereit.` Erwartet: die
   Antwort `bereit` (Probe #4 maß eine Antwortzeit von 7 s), und im Boot-Log
   die Ablage-Zeile `Ablage shinon_index_store bereitgestellt` sowie nach dem
   Turn `[shinon-scoring] Stand geladen: …`.
3. **Urteil** über die echte UI, nicht per Dienstaufruf: 'Good response' →
   'Task result' → 'Submit' (der Weg ist `messageFeedback/put` über `/api`).
   Danach neue Zeile in der Index-Ablage (`subject=<turn-id> signal=… factor=…`).
4. **Widerruf** über dieselbe Schaltfläche ('Remove rating'): die Zeile wird
   WEG, die Scorecard exakt auf den Wert zurück — dieselbe Gegenprobe, die
   Probe #4 trägt (vor dem Urteil nicht da, nach dem Widerruf weg).
5. **Host-Ende** per `npm run s6:stop` (SIGTERM), danach bestätigen: Port
   frei, Prozess beendet, erste Protokollzeilen verloren nichts.
6. **Neustart** per `npm run s6:boot`: der frische Host meldet
   `[shinon-scoring] Stand geladen: …` mit dem Stand nach dem Widerruf.

## 3. Was der Lauf als Beleg hinterlässt

Der Turn wird als Probe gespeichert in `docs/probes/s6-model-turn-<datum>.json`
— Vertragsform der probe-twin-Dateien: `id`, `claim`, `targets`, `expect`,
`result='BESTAETIGT'`, `verdict='WRITE'`, `evidence`, `evidence_note`. Harte
Zahlen des Laufs: Bootdauer, Antwortzeit, Token-/Kreditzähler der Antwort,
Ablage-Zeile, Urteil- und Widerruf-Fenster, Zähler der `Stand geladen`-Zeile
nach dem Neustart. Was er **nicht** trägt: keinen Schlüsselwert, keinen
Prompt- oder Antworttext über die Testfrage hinaus, keine UI-Bildschirm-
Fremdfragmente.

## 4. Fehlertypen

- **Preflight Exit 1** — kein Schlüsselname; der Turn wartet, der Runner hat
  nichts angefasst.
- **Preflight Exit 2** — Node zu alt, kein echtes `dsh`-Binary, `.env`-Modus
  nicht 600 (`chmod 600 .env`), dump-config-Fehler. Jede Zeile ist ein
  Stoppgrund, kein Auto-Retry.
- **Port-Kollision** — Port 3099 ist konstant (Probe #4): der Boot startet
  nichts, wenn ein anderer Prozess den Port hält; der Boot-Log nennt ihn.
- **UI ist der Kanal** — alle „Klick“-Schritte dieses Buches gehen über die
  echte Oberfläche; ein direkter `messageFeedback/put`-Aufruf auf `/api` wäre
  ein Abkürzungsbeweis, der die UI-Wege (Urteil, Widerruf) nicht belegt und
  dem Probe-Vertrag widerspricht.
